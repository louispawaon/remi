# Remi v1 implementation plan

> For agentic workers: use superpowers:executing-plans for inline implementation, or superpowers:subagent-driven-development if that execution approach is explicitly selected. Steps use checkboxes for tracking.

Date: 2026-10-28. Status: Phase 0 complete; Phases 1–7 planned.

**Goal:** Build a locally runnable, mobile-capable media card maker with reliable PNG and complete editable-project exports.

**Architecture:** SvelteKit serves the application and provider API routes. Card documents, artwork, local saving, shared Canvas rendering, and file generation live in the browser. Public hosting is deferred.

**Tech stack:** SvelteKit 3.1, Svelte 5, TypeScript 6, Vite 8, Node 24, Node adapter, Bits UI, idb, fflate, Valibot, Vitest, Playwright, and axe.

**Spec:** [Product and architecture specification](../specs/2026-10-28-remi-v1-design.md).

**Acceptance:** [Required checks and evidence](2026-10-28-remi-v1-acceptance.md).

## Global constraints

- Preserve the agreed scope, limits, defaults, API contracts, and editing/rendering invariants in the specification.
- Use SvelteKit 3 configuration rather than legacy setup examples.
- Keep credentials server-side and user uploads/card data local.
- Never discard overflow items, silently overwrite cards, or claim a failed save/export succeeded.
- Use one renderer for preview and PNG export; exact dimensions are independent of viewport and device pixel ratio.
- Complete all required mobile actions without drag-only or hover-only interactions.
- Apply Impeccable to the editor in Operate mode; approve desktop/mobile direction before production UI.
- Deliver runnable, independently testable increments. Do not provision public hosting.

## Review focus

- Sparse and over-capacity cards: preserve blanks, free space, and unplaced items across grid changes and archives.
- Asynchronous races: stale searches, overlapping saves, conflicting tabs, and edits during export cannot replace newer work.
- Mobile file actions: prepared files must be usable through actual downloads, share sheets, and file pickers.
- Trust boundaries: imported archives and proxied images cannot bypass validation or modify saved cards on failure.
- Resource limits: artwork decoding, repeated exports, and project decompression must stay bounded and release temporary resources.

## Verification commands and execution notes

Provide and run npm scripts for check, lint, unit tests, browser tests, build, and built-server startup. A fresh checkout must work with npm ci and the documented startup commands.

Run focused tests with their owning phase, followed by the complete checks at acceptance. Use deterministic provider and artwork fixtures for repeatable automated tests; record live provider checks separately.

Commit runnable, verified increments during implementation. Do not install dependencies, scaffold application files, initialize Git, or deploy as a side effect of saving these planning documents.
